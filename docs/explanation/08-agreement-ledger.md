# 顧客との合意台帳の形 (提出・承認・その後の変更)

> **TL;DR**: 提出物を出すたびに、**何を見せたか** (版・章の指紋・由来が指す正本の指紋) を追記のみの台帳に残す。
> 承認も同じ台帳に追記する。その後に章か正本が変わったら、`agreement-check` が
> **再合意が要る変更**と**通知のみの変更**に分けて出す。
> - 由来の検査が通らない提出は記録しない。出力もしない (§2)
> - 台帳が残すのは「記録した」「承認と記録した」ことだけ。合意の成立そのものは記録の外にある (§6)

## 1. 台帳の形

置き場所は**提出物のディレクトリ** (`deliverable.json` のあるディレクトリ) の直下、`agreements.ledger.jsonl`。
1 行 1 件の JSON Lines で、追記のみ。既存の行を書き換える操作は用意しない。

```jsonl
{"event":"export","version":"1.0","date":"2026-01-10","manifest":"deliverable.json","omitSections":["関連"],"chapters":[{"file":"01-reservation.md","chapterFingerprint":"sha256:9f2c...","sources":[{"from":"reservation-flow/REQ-101","fingerprint":"sha256:3b1e..."}]}]}
{"event":"approve","targetVersion":"1.0","approvedBy":"発注側の責任者","approvedAt":"2026-01-12","note":"打合せで確認"}
```

| 項目 | 中身 |
|---|---|
| `chapterFingerprint` | 提出物に出る本文の指紋。frontmatter・AUTOGEN・`omitSections` の節を除いた後の本文から計算する |
| `sources[].fingerprint` | 章の由来が指す正本の、**記録した時点**の指紋。由来の sidecar が後で書き換わっても、提出した版の記録は変わらない |
| `omitSections` | 記録した時点の設定。検査のときに同じ除去を再現するために持つ |

壊れた行が 1 つでもあれば、読む側は検査不能で止まる (黙って読み飛ばさない)。末尾が改行で終わっていない台帳には
追記しない (前の追記が途中で切れた疑いがあり、続けて書くと 2 行が繋がって両方が壊れる)。

## 2. 提出を記録する — `export --record-agreement`

| 順 | すること |
|---|---|
| 1 | manifest を読む。同じ版が既に台帳にあれば拒否する (版を上げてから提出する) |
| 2 | manifest の章に `provenance-check` と `provenance-coverage` をかける。1 件でも通らなければ拒否する |
| 3 | 通ったら、通常の出力 (HTML、PDF) を行う |
| 4 | 出力が成功したら、台帳に `export` を 1 行追記する |

2 で拒否したときは、**1 ファイルも出力しない**。由来の怪しい提出物を、合意の土台にしないためである。
`--html-only` と組み合わせたときも記録する (HTML と PDF は同じ本文から作る)。フラグを付けない `export` の
動作は変わらない。

## 3. 承認を記録する — `agreement-approve`

`igeta agreement-approve <提出物のディレクトリ> --version <版> --by <承認者> [--note "<メモ>"]`

- 承認できるのは、記録済みの版だけ。記録の無い版・台帳の無いディレクトリは検査不能
- 同じ版の承認は 1 回だけ。2 回目は違反 (台帳は追記のみで、承認を書き換えない)
- **最後に承認された版より前に提出された版は承認できない** (違反)。承認の基準は後の提出にだけ進む。
  判定は版の文字列の大小ではなく台帳上の提出順 — 版の番号付けは人の決める領域で、機械は新旧を読まない。
  古い内容に戻す合意なら、その内容で新しい版を提出してから承認する
- `--by` は必須。前後の空白・大文字小文字・全角半角をそろえて保存する

## 4. 変わったものを検査する — `agreement-check`

基準は**承認済みの版のうち、提出の記録が最も後の版**。`agreement-approve` が基準より前に
提出された版の承認を拒否するので、通常は「最後に承認された版」と一致する。
承認と提出が交差した古い台帳でも、基準が過去へ戻らないよう提出順で選ぶ。
新しい版を提出しただけ (未承認) では、基準は変わらない。

| 変わったもの | 扱い |
|---|---|
| 章の本文 (提出物に出る部分) | **再合意が要る** (違反)。新しい版を提出して承認を取る |
| 章が無くなった / 由来が指す正本が無くなった | **再合意が要る** (違反) |
| 由来が指す正本。`reagreementRules` に当たる | **再合意が要る** (違反)。正本のファイルと行を出す |
| 由来が指す正本。`reagreementRules` に当たらない | **通知のみ** (警告。終了コードは変えない) |
| 提出物に出ない節 (`omitSections`)、整形だけの変更 | 何も出さない |

承認された版がまだ無い台帳は、その旨を警告に出して適合とする (合意が無い状態は違反ではない)。
台帳が 1 つも無い案件では、何も起きない。

## 5. 再合意の規則 — `.igeta.json` の `reagreementRules`

```json
{ "reagreementRules": [
  { "kind": "requirements" },
  { "kind": "business-flow", "section": "例外の扱い" }
] }
```

正本の文書の `kind` が一致し、`section` を書いた場合は、変わった行が属する H2 の見出しも一致したときに当たる。
見出しの先頭の番号 (`1.` など) は、あってもなくても一致とみなす。既定は `requirements` の全部。
粒度は kind と節まで。表の列の単位は持たない。

## 6. CLI と終了コード

| コマンド | 種別 | 終了コード |
|---|---|---|
| `export <manifest> --record-agreement [--root <dir>] [--docs <dir>]` | 生成 | 適合 / 違反 (由来が通らない・版の重複) / 検査不能 |
| `agreement-approve <dir> --version <v> --by <name>` | 生成 | 適合 / 違反 (承認の重複) / 検査不能 |
| `agreement-check [--dir <dir>] [--docs <dir>] [--config <path>]` | 検査 (既定 OFF) | 適合 / 違反 / 検査不能 |

## 7. 限界と人が判断する地点

| 地点 | 誰が判断するか | 機械にできないこと |
|---|---|---|
| 承認の記録 | 発注側と合意を取った担当 | 「顧客が合意した」事実は記録の外 (口頭・メール等) にある。台帳は記録を残すだけで、合意の成立を保証しない |
| 承認者の名前 | 記録する人 | 表記はそろえるが、本人かどうかは確かめない |
| 再合意の要否 | 案件の担当 (`reagreementRules`) | 既定の規則は起点にすぎない。どの変更が再合意の対象かは、運用で見直す |
| 章の本文の変更 | 案件の担当 | 誤字の修正と内容の変更を区別しない。どちらも新しい版の提出と承認を求める |
| 台帳の改ざん | — | 追記のみは操作として用意しないだけで、ファイルを直接書き換えることは防げない。版管理 (git) の履歴で確かめる。壊れた行・提出物の外を指す `chapters[].file`・承認が指す提出の欠落は、検査側が検査不能で止まる (黙って読み飛ばさない)。末尾の改行の確認は途中で切れた追記の再発を防ぐだけで、壊れた台帳を機械が直すことはしない |
