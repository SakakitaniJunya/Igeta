# 人間レビュー層 (地図・決定台帳・レビューシート) を足した理由

> **TL;DR**: 1 文書 200 行の上限を守っていても、**文書が 45 枚に増えると人は読めない**。読み手の仕事
> (要件を理解して直す / コードレビューする) 基準で「人の入口 2 枚 (地図・決定台帳) + 変更単位のレビューシート」
> を足し、既存の L1 要件・L2 詳細設計はそのまま残す。
> - 採らなかった案: 設計書を減らす / 全部を人が読む / 要約を AI に都度作らせる (§2)
> - 既定は全部 OFF (段階導入)。既存プロジェクトを一斉に赤くしない (§4)

## 1. 背景 (実例 4 件。manabi-zone の SaaS 設計で実際に起きた)

| # | 実例 | 何が起きたか |
|---|---|---|
| 1 | 量 | 1 機能で設計書が約 45 ファイル・1,800 行。1 文書 200 行の上限は守っていたが、読み手の仕事単位では読める量を超えた |
| 2 | 決定の取り違え | 「CEO 2026-09-29 決定」と書かれた要件が、実際には CEO が決めていなかった例が 2 件 (評価者が発見)。仮置きの値が約 15 か所に散在し、人が「何を決め、何が未決か」を一覧できなかった |
| 3 | 虚偽報告 | 作成者の「反映済み」報告が 2 回虚偽 (実ファイル未変更)。人が確かめる手段が grep しかなかった |
| 4 | ID の取り違え | 要件 ID がファイルごとのローカル採番 (`REQ-001`〜) のため、他ファイルから「`REQ-114`」と書くとどのファイルの ID か分からない (`09-auth` の `REQ-114` と `02-tenancy` の `REQ-114` を取り違えかけた) |

いずれも「設計書 1 枚あたりの品質」の問題ではない。**文書群を横断した「今何が決まっていて、何が未決で、
どの ID がどこのものか」が機械で確かめられなかった**ことが原因。

## 2. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 設計書を減らす | 実例 1 の量は 1 機能の複雑さそのものであって、文書を減らすと今度は AI・実装者が読む情報が失われる。L1 要件・L2 詳細設計は「作る人・裁く人」向けに必要 (原則: つくる主体と裁く主体を分ける、REQ-202) |
| 全部を人が読む | 実例 1 の 45 枚・1,800 行は人間の 1 回の集中で読み切れる量ではない。「読め」と言うだけでは実例 2・3 と同じ (人が確かめる手段が無い) 状態に戻る |
| 要約を AI に都度作らせる | 要約は都度生成なので**版が固定されない** (実例 3 の「反映済み虚偽報告」と同じ構造的な弱さを持つ)。AI の要約自体が機械で検査できず、実例 2 (決定の取り違え) を再発させる。既存原則 8「サイレント縮退禁止」に反する |

## 3. 採った構成

読み手の仕事 (A: 要件を理解して直す / B: コードレビューする) に対して、**読み手別の層**を足す。

| 層 | 文書 | 読み手 | 実例への対応 |
|---|---|---|---|
| L0 地図 | `docs/00-map.md` (kind: `map`, 上限 150 行) | 人間の入口 | 実例 1: 図 1 枚 + 「詳細への入口」で量を吸収する |
| L0 決定台帳 | `docs/01-decisions.md` (kind: `decision-log`) | 人間の入口 | 実例 2・3: `DEC-nnn` / `OPEN-nnn` を機械で検査し、帰属の主張と仮置きを台帳に強制する |
| L1 要件 / L2 詳細設計 | 既存のまま | 実装者・AI | 変更しない (原則 11「1 文書は読み切れる長さ」は既に満たしている) |
| 変更単位 | PR テンプレ + `igeta review-sheet` | コードレビューする人 | 実例 4: `<doc-id>/PREFIX-nnn` の修飾 ID で対象 REQ を 1 枚に展開する |

検査 (`igeta template-check --require-human-review`) は 5 種: ①map/decision-log のテンプレ適合・行数上限
②地図が `kind: requirements` を全部リンクしているか ③決定の帰属の主張に `DEC-nnn` があり台帳に実在するか
④「仮置き」に `OPEN-nnn` があり台帳に実在するか ⑤他ファイルの ID を修飾形式で書いているか。

## 4. 段階導入・既定の強さの判断

| 論点 | 決定 | 理由 |
|---|---|---|
| 既定の強さ | ①(kind 宣言だけで opt-in) は常時、②〜⑤ は `--require-human-review` (既定 OFF) | ②〜⑤ は本文の書き方 (帰属の主張・ID 参照) を縛るので、既存プロジェクトに無警告で刺すと一斉に赤くなる。①は kind: map/decision-log を名乗った時点で opt-in なので影響が無い |
| ②〜⑤ のフラグの粒度 | 1 本のフラグに束ねた (個別 4 フラグにしなかった) | 4 つとも「人間レビュー層」という 1 つの機能の一部で、片方だけ有効にする理由が無い。個別フラグは「要求されていない柔軟性」(原則: Simplicity First) |
| 決定の帰属パターンの持ち方 | 正規表現の配列を `DocTemplateOptions` に持たせ、既定値を export する | キーワード判定は文書 lint であり、会社 OS の「選ぶ」判断 (REQ-226) ではないので regex で構わない。ただし決め打ちで隠さず、設定として見える場所に置き、プロジェクトが上書きできるようにする |
| `decision-log` の行数上限 | 付けない | `map` は「150 行に収める」ことが目的の文書だが、決定台帳は 1 決定 1 行の**台帳**で、行数は決定の数に比例して増えるのが正しい。固定の上限を付けると「決定が増えたら台帳が違反になる」という誤ったインセンティブになる |
| 修飾 ID 検査の対象範囲 | 「## 関連」節を除外する | 「関連」節は区分・文書・対応 ID の表で、隣の「文書」列が ID の帰属を常に明示している。実例 4 の問題は**本文中の裸参照**であり、関連表の対応 ID 列まで縛ると 39 種のテンプレ全部が誤検出で赤くなる |
| 決定の帰属検査の対象範囲 | decision-log 自身は除外する | 台帳は決定・仮置きの語彙 (列名「仮置き値」・見出し「仮置き一覧」) を持つのが当然で、自分自身への帰属を求めると常に誤検出する。台帳は正本であって主張ではない |

## 5. 判断に迷った点 (残った論点)

- **修飾 ID 検査の対象範囲**: 現状は kind 解決済みの doc の本文のみを見る。kind 未設定 (`unmanaged`) の doc の本文までは追わない。段階導入の第一歩としては十分だが、将来 `--require-kind` と組み合わせた時の相互作用は要確認
- **決定の帰属パターンの初期値**: company-person の実例 (「CEO 2026-09-29 決定」「〜が決定」) から採った 3 パターンのみ。他社の言い回し (「代表が承認」等) は各プロジェクトが `decisionAttributionPatterns` で追加する前提だが、CLI からの上書き手段はまだ無い (プログラム的な利用のみ)
