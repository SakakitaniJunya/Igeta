# ADR-0013: 決定の状態は承認の記録だけが変える — 状態でフォルダを分け、索引に印・根拠・持ち主を出す

> **TL;DR**: ADR の状態 (承認待ち・承認済・却下・置換) は、`igeta decision-*` の 1 つの書き込み口だけが変える。
> 変えるときは、決めた人・日付・根拠 (merge した PR か commit) を本文の履歴に追記し、状態でフォルダを分け、索引を作り直す。
> - 手書きで `accepted` にすると docs-check が落ちる。根拠の無い `accepted` は作れない
> - 索引は状態ごとの 4 つの表。承認待ちには持ち主と期限、承認済には決めた人・日付・根拠リンクを出す
> - 決定台帳 (DEC/OPEN) に状態・根拠・持ち主・期限の列を足す。Issue を入口にする案は後にする

## 関連

- **上流 (depends_on)**: ADR-0007 (文書 id で数えるので、移動しても指紋が変わらない) / ADR-0008 (`person/` は人の承認が要る)
- **下流**: 検査仕様 (テスト仕様 10)。索引が出す

## Status

2026-10-22 提案。CEO の指摘「決定が人に読めない。承認済と未承認が同じフォルダにある」を受けて起案。

## Context

ADR は AI が `proposed` で書き、CEO が PR を merge しても、状態を `accepted` に写す手順も担当も無い (ADR-0008 は強制を次の版に送った)。
Igeta 自身の 12 本は全部 `proposed` で、索引の日付は全部 `—`。索引は frontmatter を写すだけで、印・根拠・持ち主が無い。
利用側の決定台帳は、原文が引用だけで出所へのリンクが無く、OPEN に持ち主と期限が無い。保護ブランチを置けない repo があり、承認の証跡は PR の merge になる。

## Decision Drivers

- 偽造されにくい: 手書きで承認済にできず、根拠が実在する (追記のみ・書き手 1 つ・証跡必須)
- CEO が表だけで状態・根拠・待ちを読める
- 移動に耐える: 文書 id と番号は変えない
- 小さく作る: GitHub 側の自動化 (Issue 入口) は先にしない

## Decision

**採用: 状態ごとのフォルダ + 承認の履歴 (本文の追記表) + 書き込み口 1 つ**。理由: 状態の真実を、実在する根拠を持つ追記の記録 1 か所に置けるため。

| 判断軸 | 採用案 | 理由 |
|---|---|---|
| 1 フォルダ | `person/decisions/` の下に `proposed/` (年なし) / `accepted/<年>/` (accepted・amended) / `rejected/<年>/` / `retired/<年>/` (superseded・deprecated)。年は承認・却下した年。`01-decisions.md` と `README.md` は直下 | 承認待ちは数が少なく年で分けない。年は残す (置き場所の表と 15 本の対象外の規則を保つ)。置換は旧い承認の年のまま `retired/` へ |
| 2 書き手 | `decision-accept` / `reject` / `supersede` / `amend` の 4 動詞が 1 つの書き込み口 (`recordDecision`) を通る。本文の「承認の履歴」に 1 行追記し、`status` を写し、ファイルを移し、リンクを書き換え、索引を作り直す。全部書くか何も書かない | 書き手が 2 つあると、状態と履歴が食い違う |
| 3 証跡 | 承認・却下・改訂には、決めた人 (`.igeta.json` の `decisions.approvers` の名前) と根拠の URL を必須にする。承認・改訂の根拠は同じ repo の merge 済み PR か commit。CLI は `gh` で、merge した人が決めた人の GitHub 名であること・根拠 commit がいまの履歴にあること・その時点の本文の指紋がいまの本文と同じことを確かめる。確かめられなければ書かない (検査不能) | 推測で埋めない。偽の根拠は、実在する commit に自分の本文が入っていることまでは作れない |
| 4 検査 | `status` は履歴の最後の行の写し。違えば落ちる。履歴は追記のみ (対象 branch との比較)。承認後の本文変更は落ちる (改訂は `amend`)。フォルダと `status` の不一致・同じ id か番号が 2 つ・置換の片側だけ・許可されない遷移も落ちる | 手書きの変更を、行の有無・根拠の実在・本文の指紋で見分ける |
| 5 待ち | 承認待ちは `awaiting` (持ち主) を必須にし、`due` は任意。承認待ちが対象 branch に入ってから `decisions.staleDays` (既定 14) 日を超えるか、期限を過ぎたら、持ち主付きの警告を出す。`igeta decision-pending` が経過日数と、実行すべき accept の候補を出す | 日付で違反が増えると CI が日によって赤くなる。違反にせず警告にする |
| 6 覆す | `supersedes` と `superseded_by` は対。新しい ADR が承認済になってから `decision-supersede` で旧い方を `retired/` へ移す。根拠は新しい ADR の承認の根拠 | 双方向に辿れ、片側だけの状態を作らない |
| 7 索引の表 | 4 つの表。承認待ち: 起案日・持ち主・期限。承認済: 承認日・決めた人・根拠リンク・覆す先。却下: 却下日・決めた人・根拠。置換: 置換日・覆した ADR。状態は絵文字 + 語 (✅ 承認済 / ⏳ 承認待ち / ❌ 却下 / ↪ 置換)。語を検査の対象にし、絵文字と語の食い違いは落とす。経過日数は索引に入れない (同じ入力は同じ出力) | GitHub・VS Code・端末で読める。`[x]` は表で描画されず、リンクの記法と紛れる |
| 8 台帳 | DEC: ID・状態・日付・決めた人・原文・根拠・決定・影響する文書。OPEN: ID・状態・論点・推奨案・暫定値 (現行の値の列)・持ち主・期限・根拠・影響する文書。根拠は PR・Issue・会議録・fd のリンク。状態は最後の列に置かない (決まりの表と別物にする) | 原文だけでは出所を辿れない。OPEN は持ち主と期限が無いと放置される |
| 9 移行 | 12 本は、下の根拠で `decision-accept` を通す。根拠の無い旧 `accepted`・`rejected` は、記録の上で `proposed/` へ差し戻す (履歴に旧い状態を残す)。利用側は `docs-migrate` に 1 段を足す | 根拠を作って承認済にしない |
| 10 再発防止 | `init` の AGENTS.md と人の承認の手引きに「PR を merge したら `decision-pending` を実行し、記録の PR を出す」を置く。記録の PR は `person/` を触るので、CEO がもう一度 merge する | 手順と担当を文章にする |

**Igeta 自身の 12 本の根拠** (merge は全部 SakakitaniJunya。実行時に `gh` が再確認する): 0001〜0010 は PR #19 (2026-10-05)、0011 は PR #20 (2026-10-08)、0012 は PR #26 (2026-10-22)。
承認済にする前に、要件か設計の決まりの行が `ADR-NNNN` を引いていること (docs-check の引用の検査)。0006・0007・0010・0012 は引く行がまだ見当たらないので、先に足す。

## 却下した選択肢

- **索引だけ直す (フォルダは分けない)**: CEO の要望に合わず、承認済と未承認が同じ場所に残る
- **frontmatter の `status` を人が書き換える運用に戻す**: いまの失敗そのもの。誰が・いつ・何を根拠にが残らない
- **PR の中で作者が `accepted` と書く**: 自分の承認を自分で書く。根拠の PR がまだ merge されていない
- **台帳を JSONL の別ファイルにする**: 置ける場所の表に無い (docs/ に置けるのは表の kind だけ)。本文と離れて食い違う
- **GitHub Issue を入口にして `decisions-sync` で表を作る (先行案 09・10)**: 後にする。理由は Consequences
- **承認の自動記録 (Actions が merge で書く)**: 書き手が bot になり、人の承認の証跡と区別できない。後にする

## Consequences

- 良い方向: 状態・根拠・待ちが表で読め、手書きで承認済にできない。代償: 承認ごとに記録の PR が要り、CEO の merge が 2 回になる
- 承認前に GitHub-front を採ると、Issue の編集・削除と ID の二重採番 (`#123` と DEC) を同時に持つ。根拠欄は Issue の URL も受けるので、後から入口を足しても台帳の形は変えない
- 保証しないこと: AI と CEO が同じ GitHub アカウントのとき、merge した人が人かは見分けられない (ADR-0008 の限界 3)。偽造を防ぐのではなく、実在しない根拠・承認後の本文変更・手書きの状態を落とす

## Confirmation

| 手段 | 対象 | 落ちる条件 |
|---|---|---|
| テスト仕様 10 (DS1〜DS14) | docs-check・`decision-*` | 表のテストが 1 件でも落ちる |
| `docs-check` | 状態・履歴・フォルダ・台帳の列 | 手書きの `accepted`・根拠の欠け・不一致 |

## 再検討トリガ

- 承認待ちのまま、merge から 30 日を超えた ADR が 3 本以上になったら、自動記録 (Actions) と Issue 入口を設計する
- 1 つの repo で、記録の PR を CEO が 3 回続けて確かめずに merge したら、記録の PR を分ける運用を見直す
