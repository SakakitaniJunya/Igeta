# ADR-0001: docs/ の第1階層を「誰が確定させるか」で 3 つに分ける

> **TL;DR**: docs/ 直下は `person/`・`ai/`・`client/` の 3 つ。分ける基準は読み手ではなく、**確定させる人**。
> `person/` = 確定する前に人が全部読んで承認する文書。変わったら、変わった行を人が読んで承認する。
> `ai/` = AI が書き、評価する AI が確定させる文書。人の承認は要らず、人は決めるために読む必要がない。
> `client/` = 顧客と合意して渡す文書。「人も AI も読む」置き場所 (`common/`) は作らない

## 関連

- **上流 (depends_on)**: [要件定義書 — 読み手別ディレクトリ](../product/02-audience-directories.md)
- **下流**: ADR-0002〜0010

## Status

2026-10-02 提案 (v4)。v1〜v3 は取り下げた。v3 (`common`/`ai`/`person`/`client`) は実装前に撤回した。

## Context

v3 は「誰が読むか」で分けたため、人も AI も読む文書の置き場所 `common/` が要り、曖昧な境目になった。
実案件 1 件では、設計を判断する図 42 枚のうち 41 枚が `ai/` 側にあり、人が決めるべき業務の決まりや画面が
人の読まない場所にあった。逆に基本設計をそのまま `person/` へ移すと、37 本・約 31 万字で読みきれない。
原因は置き場所ではなく、1 本に「人が決める内容」と「作り方」が混ざっていることだった。

## Decision Drivers

- 境目が 1 つの問いで決まり、機械で強制できること / `person/` に読まなくてよい文書を置かないこと
- 人が決める設計が `person/` だけで揃い、全部読める量に収まること

## Decision

**採用: 確定させる人で 3 つに分ける。**

| フォルダ | 置くもの | 確定させる人 | 人が開くとき |
|---|---|---|---|
| `docs/person/` | 人の承認なしに変えてはいけない決まりと、その決定の記録 | 人 | 確定前に全部読む |
| `docs/ai/specs/` | 作り方の詳細 (詳細設計・実装タスク) | 評価する AI | 読む必要はない |
| `docs/ai/handbook/` | 作業の手引き (手順書・解説・障害の手順)。決まりは書かない | 評価する AI | その作業をするときに開く |
| `docs/client/` | 顧客に渡して合意するもの | 人と顧客 | 渡す前に全部読む |

**置き場所を決める問い (1 つだけ)**: 「AI がこれを勝手に変えたら、事業・お金・顧客との約束・使う人の体験・
法令のどれかが変わるか」。変わるなら `person/`、変わらないなら `ai/`。kind 単位で振り分け (ADR-0009)、
混ざった雛形は節の単位で組み直す (ADR-0010)。

```text
AGENTS.md          ← AI の入口 (person/ を上流、ai/ を持ち場として指す)
docs/
├── person/        ← requirements/・design/{shared,<まとまり>}/・decisions/
├── ai/            ← specs/{shared,<まとまり>,tasks}/・handbook/{how-to,explanation,runbooks}/
└── client/        ← delivery/・proposals/
```

kind 47 種の置き場所は要件定義書 02 §7 (決定は ADR-0009)、型と量は ADR-0002、承認が要る変更の見分けは ADR-0008。
実測では、業務フロー 3 本を ID を変えずに人の型へ書き直すと、本文が元の 26% になった。
フォルダ名は小文字 (既存が全部小文字。macOS と Linux で大文字小文字の扱いが違う)。

## 却下した選択肢

- **v3 (読み手で 4 分割、`common/` あり)**: 「両方が読む」が曖昧な境目になる
- **宛先で 3 分割し、基本設計を `ai/` に置く**: 人が判断する図と決まりが `person/` に無く、設計を作りきれない
- **基本設計をそのまま `person/` へ移す**: 読みきれない。移すのではなく、書き直す必要がある
- **`person/` を「必ず読む」と「決めるときだけ開く」の 2 段にする**: 読まなくてよい文書が人の場所に入る
- **手順書・解説を `person/` に置く**: 決まりではないので承認が要らない。置くと人の待ち行列を手順書の更新が埋める

## Consequences

- 良い方向: 置き場所がそのまま承認の要否になる。モデルが強くなって詳細設計が要らなくなっても、`person/` は残る
- 代償: 既存の基本設計は、人が決める内容と作り方に**書き直す**作業が要る (ADR-0003)。AI は `person/` も読む
- 限界: 置き場所が正しいことが前提。AI が人の決定 (金額・期限) を `ai/` に書いてしまうと、機械では
  見分けられない。`review-sheet` が「`ai/` の行に金額・率・期限らしい語があり、`person/` の ID を引かない行」を
  一覧にするだけで、門にはならない。評価する AI と、人のレビューで見つける

## Confirmation

| 手段 | 対象 | 落ちる条件 |
|---|---|---|
| `RoleBoundaryCheck` (新設、ADR-0002) | 3 フォルダ配下の全文書 | kind から導く置き場所と実際のパスが食い違う |
| `PersonFormCheck` (新設、ADR-0002) | `person/` の文書 | 型 (状態の列・図)・量・`ai/` を指す参照のどれかが崩れている |
| `approval-scope` (新設、ADR-0008) | 変更の差分 | `person/`・`client/` を含む変更を「人の承認が要る」と判定しない |
