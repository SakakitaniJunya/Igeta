# 予約 CLI サンプルのリスクと技術的負債

> **TL;DR**: 意図して先送りしたのは、2 集約の原子性・重複作成の拒否・認可の 3 つ。いずれも返済条件を決めてある。
> - 本書は「設計上どう効くか」の要約。課題管理台帳は持たない (学習用サンプルのため)
> - 知らずに積んだものは負債ではなく欠陥として直す

## 1. 技術リスク

| ID | リスク | 確率 | 影響 | 早期兆候 | 対応 |
|---|---|---|---|---|---|
| RSK-001 | 学習者がサンプルのテナント分離を認可の実装例と誤解する | 中 | 高 | 「RLS はどこ?」という質問 | 各文書とサンプル README に「認可の代わりにならない」と明記 (低減) |
| RSK-002 | 設計書だけ増えて実装と検査が追いつかない | 中 | 中 | `sample:check` に含まれない文書が増える | 文書追加時に検査手段を 1 つ決める。無ければ「未整備」と書く (低減) |
| RSK-003 | Node.js の `--test` 仕様変更で検査が動かなくなる | 低 | 中 | CI の `sample:test` が構文で落ちる | engines を `>=22` に固定。破損時は Runbook に従う (受容) |

## 2. 技術的負債

| ID | 内容 | 負債を負った理由 | 返済条件 (何が起きたら返す) | 決定元 ADR |
|---|---|---|---|---|
| RSK-101 | 確定・キャンセルが 2 集約を順次保存し、途中失敗の補償が無い | メモリ adapter にトランザクションが無い。学習の主眼が設計書の対応関係にある | DB adapter を採用したとき。トランザクション境界かサーガのどちらかを設計してから実装する | [ADR-0001](../adr/0001-in-memory-persistence.md) |
| RSK-102 | 同一テナント・同一 ID の再作成が上書き保存になる | 冪等性の要件が学習シナリオに無い | 実案件の冪等性要件を決めたとき。冪等キーと重複時の応答を先に決める | — |
| RSK-103 | イベント配信が失敗しても保存済みの予約は残る | 補償処理を入れると学習用コードが倍になる | 購読側を作るとき。再送か発行済みテーブルのどちらかを設計してから実装する | — |
| RSK-104 | 文言の直書きを機械で検出していない | カタログの参照漏れを検出する仕組みが未整備 | 文言の重複が実際に起きたとき。lint ルールを追加する | — |

## 3. 受容したリスク

| ID | リスク | 受容の理由 | 再評価のトリガ |
|---|---|---|---|
| RSK-201 | 認証・認可・行レベルセキュリティを実装しない | 学習の範囲外。実装すると準備が増え、主眼がぼやける | サンプルを外部公開する形に変えるとき |
| RSK-202 | 画面・HTTP・DB の設計書 (画面設計・API 仕様・テーブル定義) を書かない | 実装が無い状態で書くと、検査できない設計書が増える | サンプルに HTTP 面か画面を追加するとき |
| RSK-203 | 枠が時間帯を持たず、重複判定をしない | 枠管理の方式は案件ごとに違い、サンプルで固定すると誤解を招く | 実案件の枠管理方法を決めたとき |
